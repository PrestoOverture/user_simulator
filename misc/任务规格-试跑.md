# 任务规格：中文售后客服用户模拟器真实性——20 段对话试跑

## 0. 一句话目标

用 20 段真实的中文售后客服对话，比较"真人用户说的下一句话"和"Spark 2.6 扮演用户说的下一句话"。产出一张并排对照表、一组规则统计和实际 token 用量，用来决定第一阶段的核心测量指标。

**这是试跑，不是正式实验。** 目标是看清数据、跑通管线、找出差距最明显的行为。不要过度工程化。

## 1. 背景（只读，不需要执行）

- 研究方向：LLM 用户模拟器在真实业务中的失真。已知研究发现，模拟用户过于配合、礼貌、话太长，不会放弃或升级，导致 agent 评估结果虚高。
- 详细文献和数据源见附带的 Gemini 研究报告（`LLM用户模拟器蓝海场景研究.md`），本任务只用到其中第 2 节的数据集信息。
- 报告中的链接和数据描述**尚未核实**，执行时以实际下载到的数据为准。

## 2. 约束

- 语言：Python 3.11+，普通脚本即可，不引入 agent 框架。
- 模拟器模型：**只用讯飞星辰 Spark 2.6**。不要因为调用失败就静默换成别的模型。
- API 凭证从环境变量读取，不写进代码或日志。
- Spark 的接口细节（地址、鉴权方式、参数名）**以讯飞官方文档为准**，不要凭记忆编写。
- 试跑 token 上限：200 万。接近上限时停止并报告。
- 所有随机抽样固定随机种子，并记录在输出里。

## 3. 停止条件（遇到时停下并报告，不要自行绕过）

- CSDS 无法下载，或下载后格式与预期差别很大。
- Spark API 无法调用，或使用条款不允许这类用途。
- token 用量接近上限。

## 4. 步骤

### 第 0 步：确认 Spark

1. 查阅官方文档，确认：免费额度的有效期、速率限制（RPM/TPM）、使用条款是否允许研究用途。
2. 用一条最简单的请求测试调用是否成功。
3. 结果写入 `outputs/spark_check.md`。

### 第 1 步：获取并检查 CSDS

1. 数据来源（来自 Gemini 报告，需要核实）：GitHub `xiaolinAndy/CSDS`；仓库 README 中给出了百度网盘和 Google Drive 下载链接。
2. 下载后**先不要写处理代码**，先回答以下问题，写入 `outputs/data_format_notes.md`：
   - 一段对话的数据结构是什么样的？说话人如何标注？
   - **用户连发多条消息时，是分开记录还是合并成一条？**
   - 是否有用户诉求摘要（User Summary）？内容是否包含对话的最终结果（例如"最终退款成功"）？
   - **是否有标注说明问题最终是否解决？**
   - 数据总量，以及每段对话的平均轮数。
3. 附上 3 段完整对话的原文样例。

### 第 2 步：抽样

1. 从数据中随机抽取 20 段对话，固定随机种子。
2. 优先选择轮数在 6 到 30 之间的对话，太短没有信息，太长成本高。
3. 记录被抽中的对话 ID。

### 第 3 步：逐轮重放

**定义"用户轮次"：** 两次客服发言之间，用户发出的全部消息合并为一个用户轮次。如果用户连发了多条，用换行符分隔保留。

对每段对话中的**每一个用户轮次 t**：

1. 输入给模拟器的内容：
   - 角色设定：你是一位在京东购物后联系售后客服的普通顾客。
   - 任务目标：该对话的用户诉求摘要。如果摘要中包含对话结果，**删去结果部分**，只保留诉求，并在 notes 里说明删除规则。
   - 对话历史：真实对话中第 t 轮之前的全部内容，包括真实客服的发言。
   - 指令：只输出顾客的下一句话；使用自然、口语化的中文聊天风格；如果要连发多条消息，用换行分隔。
2. 不要输入第 t 轮及之后的任何内容。
3. 每个轮次只生成一次。temperature 使用官方默认值，并记录下来。
4. 保存完整的 prompt 模板到 `outputs/prompt_template.md`。

### 第 4 步：规则统计

对真人和模拟器的每一个用户轮次，分别计算以下指标。**关键词列表都是暂定的**，放在单独的配置文件里，方便修改。

| 指标 | 计算方法（暂定） |
|---|---|
| 字数 | 去掉标点和空白后的汉字和字母数字数量 |
| 短句率 | 字数 ≤ 5 的轮次比例 |
| 连发条数 | 一个用户轮次中包含的消息条数 |
| 礼貌词频率 | 命中"您好、谢谢、麻烦、请、辛苦、不好意思"等词的轮次比例 |
| 升级要求 | 命中"主管、经理、领导、投诉、差评、12315、举报、工商"等词的轮次比例 |
| 拒绝方案 | 命中"不要、不行、不接受、不同意、我要退款"等词的轮次比例 |
| 催促 | 命中"快点、多久、到底、什么时候、怎么还、赶紧"等词的轮次比例 |
| 重复追问 | 与该用户之前任一轮次的字符相似度（difflib ratio）> 0.6 的轮次比例 |
| 首轮信息量 | 第一个用户轮次的字数，以及是否包含 8 位以上数字（视作订单号） |
| 自我更正 | 命中"不对、说错了、不是……是、我是说"等表达的轮次比例 |

### 第 5 步：记录成本

记录试跑的输入 token、输出 token、请求次数和总耗时；按全部数据量推算正式实验的 token 用量。写入 `outputs/token_usage.json`。

## 5. 输出文件

```
outputs/
  spark_check.md          第 0 步结果
  data_format_notes.md    第 1 步结果（含 3 段样例）
  sampled_ids.json        抽中的对话 ID 和随机种子
  prompt_template.md      完整 prompt 模板和参数
  side_by_side.csv        对话ID | 轮次 | 上下文最后两轮 | 真人原话 | Spark 输出
  metrics_by_turn.csv     每一轮次的全部指标（真人和模拟器各一行）
  metrics_summary.md      各指标的真人均值、模拟器均值、差距，按差距大小排序
  token_usage.json        第 5 步结果
  report.md               总结报告（见第 6 节）
```

## 6. 总结报告 `report.md` 必须回答

1. 数据格式中有哪些与预期不同的地方？对后续实验有什么影响？
2. 哪些指标在真人数据中**足够常见**？哪些太罕见，测不出结论？
3. 哪些指标的真人与模拟器差距**最明显**？列出前 3 项，并各附 2 个并排对照的典型例子。
4. 有没有规则统计捕捉不到、但阅读对照表时明显感受到的差异？
5. 关键词规则有哪些明显的误判？
6. 按实际 token 用量推算，正式实验需要多少 token？Spark 额度是否足够？

报告只陈述观察到的事实，不要写"这证明了……"之类的推断。

## 7. 可选分工（使用两个 agent 时）

- 一个 agent 负责实现和运行。
- 另一个 agent 负责审查：检查重放时是否泄露了第 t 轮之后的内容，检查摘要中的结果是否已经删除，抽查 20 条关键词规则的命中是否合理。
